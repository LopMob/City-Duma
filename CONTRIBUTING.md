# Правила внесения изменений
=-
## 1. Порядок работы над задачей

1. Задача уже описана в `docs/tasks/ISSUE-*.md` — критерии приёмки там.
2. Создать ветку от `main`: `feature/<имя-из-docs/TASKS.md>`.
3. Вносить изменения небольшими, осмысленными коммитами
   (`git commit -m "add X"`, `git commit -m "test X"`, `git commit -m "docs: X"`) —
   не одним большим коммитом на всю задачу.
4. Перед push и перед PR — обязательно `make verify`.
5. Открыть Pull Request в `main` со ссылкой на соответствующий
   `docs/tasks/ISSUE-*.md`.
6. После ревью — слияние в `main`, удаление ветки.

## 2. Обязательные локальные команды перед PR

```
make quality   # ruff + black --check
make sast      # bandit — статический анализ безопасности
make test      # pytest + покрытие (порог — см. pyproject.toml, не менее 40%)
make verify    # quality + sast + test одной командой — обязательна перед push/PR
make backup    # резервная копия текущей БД (scripts/db_backup.py)
make restore FILE=backups/duma_<ts>.sql   # восстановление из копии
```

Назначение каждой команды внутри `make verify` подробно объяснено в
`docs/VERIFY.md` (готовый ответ на вопрос «объясните, что делает каждая
команда» на защите).

## 3. Запрещённые действия

- Удалять или пропускать существующие тесты, чтобы «протолкнуть» изменение.
- Снижать порог покрытия `--cov-fail-under` в `pyproject.toml`, чтобы
  обойти упавшую проверку, вместо того чтобы дописать тесты.
- Добавлять подавления находок анализаторов (`# noqa`, `# nosec`,
  `# type: ignore` и т.п.) без явного обоснования в соседнем комментарии
  и упоминания в PR, почему именно здесь это безопасно. Любое такое
  исключение — это самостоятельное решение автора, за которое он отвечает
  на защите; «чтобы прошла проверка» не является обоснованием.
- Коммитить `.env`, реальные секреты, `*.db`.
- Прямой push в `main`, минуя ветку и PR.
- Мержить PR с конфликт-маркерами (`<<<<<<<`) в коде.
- Любое из вышеперечисленного, даже временно «на один коммит» — правило
  действует всегда, не только «в проде».

## 4. Definition of Done

1. Есть задача (`docs/tasks/ISSUE-*.md`), ветка, минимум 2–3 осмысленных
   коммита с понятными сообщениями.
2. `make verify` проходит локально.
3. Реализовано минимум одно содержательное бизнес-правило задачи (если
   оно есть в критериях приёмки).
4. Обновлён `docs/DATA_MODEL.md`, если менялась схема данных.
5. Автор способен объяснить каждую строчку своего diff — на защите
   спрашивают именно про это.

## 5. Ветвление и версии

- `main` — всегда рабочая, покрытая тестами ветка.
- `feature/*` — одна задача = одна ветка = один автор.
- Версии — семантическое версионирование (`v0.1.0` — первая версия).
