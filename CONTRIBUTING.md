# Правила внесения изменений
=-
## 1. Порядок работы над задачей

1. Задача уже описана в `docs/tasks/ISSUE-*.md` — критерии приёмки там.
2. Создать ветку от `main`: `feature/<имя-из-docs/TASKS.md>`.
3. Вносить изменения небольшими, осмысленными коммитами
   (`git commit -m "add X"`, `git commit -m "test X"`, `git commit -m "docs: X"`) —
   не одним большим коммитом на всю задачу.
4. Перед push и перед PR — обязательно `make verify`.
5. Открыть Pull Request в `main` со ссылкой на соответствующий
   `docs/tasks/ISSUE-*.md`.
6. После ревью — слияние в `main`, удаление ветки.

## 2. Обязательные локальные команды перед PR

```
make db-init   # один раз: создать рабочую и тестовую БД PostgreSQL
make quality   # ruff + black --check
make sast      # bandit — статический анализ безопасности
make test      # pytest + покрытие (нужен запущенный PostgreSQL; порог — не менее 40%)
make verify    # quality + sast + test одной командой — обязательна перед push/PR
make backup    # резервная копия текущей БД (scripts/db_backup.py)
make restore FILE=backups/duma_<ts>.sql   # восстановление из копии
make container-check   # ЛР4: контейнерное окружение (обязательно при любых правках Docker-файлов)
make guard             # ЛР5: какие критические файлы затронуты и нет ли ослабления проверок
make ci-local          # ЛР5: всё, что проверяет CI, на своей машине
```

**CI (ЛР5).** Те же команды выполняет pipeline GitLab CI/CD
(`.gitlab-ci.yml`, описание — `docs/CI.md`) на каждый push, MR и изменение
`main`. MR сливается только при зелёном pipeline; образ публикуется в
registry только после успеха всех проверок.

**Контейнерное окружение (ЛР4).** Любое изменение `Dockerfile`, `.dockerignore`,
`compose.yaml`, `requirements-runtime.txt` или контейнерных скриптов допускается
только после успешного `make container-check` (быстрая проверка файлов без
Docker — `make container-lint`). Подробности — `docs/CONTAINER.md`.

Назначение каждой команды внутри `make verify` подробно объяснено в
`docs/VERIFY.md` (готовый ответ на вопрос «объясните, что делает каждая
команда» на защите).

## 3. Запрещённые действия

- Удалять или пропускать существующие тесты, чтобы «протолкнуть» изменение.
- Снижать порог покрытия `--cov-fail-under` в `pyproject.toml`, чтобы
  обойти упавшую проверку, вместо того чтобы дописать тесты.
- Добавлять подавления находок анализаторов (`# noqa`, `# nosec`,
  `# type: ignore` и т.п.) без явного обоснования в соседнем комментарии
  и упоминания в PR, почему именно здесь это безопасно. Любое такое
  исключение — это самостоятельное решение автора, за которое он отвечает
  на защите; «чтобы прошла проверка» не является обоснованием.
- Коммитить `.env`, `.env.compose`, реальные секреты, резервные копии (`backups/`).
- В контейнерном окружении (ЛР4) запрещено — и это проверяет `make container-check`:
  1. образы с тегом `latest` или без тега (версии закрепляются точно);
  2. запуск процессов от root (в `Dockerfile` обязателен непривилегированный `USER`);
  3. секреты в образе (`ENV`/`ARG` с паролями, `COPY .env`, ключи) и пароли
     литералами в `compose.yaml` — только `${ПЕРЕМЕННЫЕ}` из `.env.compose`;
  4. отключение healthcheck (`HEALTHCHECK NONE`, `healthcheck: disable`);
  5. публикация лишних портов: порт БД не публикуется никогда, наружу
     открыт только HTTP-порт приложения.
- Прямой push в `main`, минуя ветку и PR.
- В CI (ЛР5) запрещено: удалять обязательные jobs, добавлять им
  `allow_failure`, `when: manual`, `|| true`, вычёркивать команды из jobs и
  make-целей, давать `publish:image` возможность стартовать до окончания
  проверок (`needs`), хранить пароли и токены в репозитории (только
  Masked-переменные GitLab).
- Мержить PR с конфликт-маркерами (`<<<<<<<`) в коде.
- Любое из вышеперечисленного, даже временно «на один коммит» — правило
  действует всегда, не только «в проде».

## 3а. Критические файлы приёмки (ЛР5)

Перечислены в `.gitlab/CODEOWNERS`: тесты, `Makefile`, `pyproject.toml`,
`requirements.txt`, `.gitlab-ci.yml`, `.gitlab/`, `.gitleaks.toml`,
`.gitleaksignore`, `.trivyignore`, скрипты-проверки, этот файл, `docs/CI.md`,
`docs/VERIFY.md`.

- Любое изменение критического файла видно в MR: job `guard:critical-files`
  перечисляет такие файлы и их владельцев.
- MR с такими изменениями сливается только после **Approve владельца из
  CODEOWNERS, который не автор MR**, данного после последнего push; затем
  Retry job guard.
- Ослабление проверок (удалённый тест, меньше `assert`, `skip`, снижение
  порога, новое исключение анализатора, убранный шаг) guard называет явно;
  в описании MR обязательно обоснование.
- Перед push: `make guard` — показывает то же, что увидит reviewer.

## 4. Definition of Done

1. Есть задача (`docs/tasks/ISSUE-*.md`), ветка, минимум 2–3 осмысленных
   коммита с понятными сообщениями.
2. `make verify` проходит локально.
3. Реализовано минимум одно содержательное бизнес-правило задачи (если
   оно есть в критериях приёмки).
4. Обновлён `docs/DATA_MODEL.md`, если менялась схема данных.
5. Если менялось контейнерное окружение — `make container-check` проходит.
5а. Pipeline MR зелёный; изменения критических файлов одобрены владельцем.
6. Автор способен объяснить каждую строчку своего diff — на защите
   спрашивают именно про это.

## 5. Ветвление и версии

- `main` — всегда рабочая, покрытая тестами ветка.
- `feature/*` — одна задача = одна ветка = один автор.
- Версии — семантическое версионирование (`v0.1.0` — первая версия).
