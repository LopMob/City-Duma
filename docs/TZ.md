# Техническое задание — «Городская Дума»

## 1. Назначение системы

Система предназначена для учёта депутатов городской думы, комиссий, их
председателей, заседаний и посещаемости депутатами заседаний. Используется
аппаратом думы для ведения актуального реестра и подготовки отчётов по
посещаемости за период.

## 2. Категории пользователей

| Роль | Возможности |
|---|---|
| Секретарь думы / администратор | Полный доступ: ведение депутатов, комиссий, состава, заседаний, отметка посещаемости |
| Сотрудник аппарата комиссии | Работа с заседаниями и посещаемостью «своей» комиссии |
| Наблюдатель / депутат | Только чтение: списки, статусы заседаний, отчёты по посещаемости |

В ЛР1 система не содержит аутентификации/авторизации; API открыт, но
структурирован так, чтобы роли можно было наложить позже без изменения
модели данных.

## 3. Основные сценарии использования

1. Секретарь регистрирует депутата и включает его в состав комиссии.
2. Секретарь назначает председателя комиссии.
3. Секретарь создаёт заседание комиссии с датой и повесткой.
4. По итогам заседания отмечается посещаемость каждого приглашённого депутата.
5. Заседание переводится в статус «проведено» — при этом проверяется кворум.

## 4. Обязательные правила работы (бизнес-правила)

- **Один председатель на комиссию.** У комиссии не может быть более одного
  депутата с флагом `is_chair = true` одновременно — `409 Conflict`.
- **Кворум.** Заседание нельзя перевести в статус `held`, если число
  депутатов со статусом `present` не превышает половины списочного состава
  комиссии. Не применяется к пленарным заседаниям (`commission_id = null`).
- **Уникальность членства.** Один депутат не может быть дважды включён в
  одну и ту же комиссию.
- **Уникальность отметки посещаемости.** На одном заседании у одного
  депутата — только одна отметка.

## 5. Сущности и связи

См. `docs/DATA_MODEL.md`. Минимум по заданию (не менее трёх связанных
сущностей) закрывается уже связкой `Deputy` — `CommissionMembership` —
`Commission`; `Meeting`/`Attendance` реализуются сверх минимума.

## 6. Ограничения

- Имя депутата — от 2 до 255 символов, обязательно.
- Название комиссии — уникально.
- Статус заседания: `scheduled`, `held`, `cancelled`.
- Статус посещаемости: `present`, `absent`, `excused`.
- Удаление депутата/комиссии каскадно удаляет связанные записи.

## 7. Обработка ошибок

| Код | Ситуация |
|---|---|
| 404 | Депутат/комиссия/заседание с указанным id не найдены |
| 409 | Нарушение бизнес-правила: второй председатель, дублирующее членство/посещаемость, отсутствие кворума |
| 422 | Некорректное тело запроса |

Единый формат: `{"detail": "человекочитаемое описание"}`.

## 8. Требования к хранению данных

- Реляционная СУБД, SQLite (файл `duma.db`) для ЛР1; строка подключения —
  через `DATABASE_URL`.
- Схема управляется миграциями Alembic (`alembic/versions`).

## 9. Веб-интерфейс

Обязателен по заданию ЛР1. Лёгкий статический дашборд поверх API, без
отдельного frontend-фреймворка и сборки. Подробности — `docs/UI.md`.
