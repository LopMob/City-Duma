# Разделение работы по команде (ЛР1)

Проект разбит на три задачи по сущностям, каждая — отдельная ветка и
отдельный PR в `main`, по правилам из `CONTRIBUTING.md`.

| # | Участник      | Сущности                              | Ветка                              | Статус         |
|---|---------------|----------------------------------------|-------------------------------------|----------------|
| 1 | (вы)          | `Deputy`, `Commission`                 | `feature/deputies-commissions`      | готово, в `main` |
| 2 | одногруппник 1| `CommissionMembership` + правило «один председатель» | `feature/commission-membership` | готово, PR в `main` |
| 3 | одногруппник 2| `Meeting`, `Attendance` + правило «кворум» | `feature/meetings-attendance` | см. `docs/tasks/ISSUE-3-meetings-attendance.md` |

Порядок задач не случаен: #2 и #3 зависят от таблиц `deputies` и
`commissions`, поэтому они стартуют после мержа задачи #1 в `main`.
#2 и #3 между собой не пересекаются и могут делаться параллельно.

## Как включиться в задачу (для #2 и #3)

1. `git checkout main && git pull`
2. `git checkout -b feature/<имя-ветки-из-таблицы>`
3. Добавить свои модели в `app/models.py`, схемы — в `app/schemas.py`,
   CRUD — в `app/crud.py`, роутер — в `app/routers/`, подключить роутер
   в `app/main.py`.
4. Добавить свою миграцию Alembic (`alembic revision --autogenerate -m "..."`),
   проверить её содержимое руками.
5. Написать тесты в `tests/`.
6. `make verify` перед push.
7. PR в `main` со ссылкой на соответствующий `docs/tasks/ISSUE-*.md`.

Все обязательные правила — в `CONTRIBUTING.md`.

### Как сделать пункт 9 (конфликт слияния) для защиты

Самый естественный способ — не подстраивать искусственно, а просто дать
двум веткам подряд задеть один и тот же файл (обычно это `README.md` или
`docs/DATA_MODEL.md`, которые правят все). Например:

1. В ветке `feature/commission-membership` и в `main` (или в другой
   фиче-ветке) независимо отредактировать один и тот же абзац
   `docs/DATA_MODEL.md`.
2. Смержить первую ветку в `main` — без проблем.
3. При мерже второй — Git покажет конфликт в этом файле.
4. Открыть файл, вручную выбрать/скомбинировать правильный вариант,
   убрать маркеры `<<<<<<<`/`=======`/`>>>>>>>`, закоммитить, завершить
   слияние.
5. На защите — показать сам факт конфликта (`git log --merges`, снимок
   с маркерами) и объяснить, как разрешили.
